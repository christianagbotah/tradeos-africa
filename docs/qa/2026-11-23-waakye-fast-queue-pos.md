# TradeOS Quick Serve for waakye sellers and busy microvendors

The seller opens Sell > Quick Serve. The device remembers that preference for
the active business and branch. First-time setup uses the existing Catalog:
add prepared Waakye portion (₵10), Gari (₵2), Fish (₵20), Egg (₵8), or
other variants, and optionally pin the items to the first screen. This is not
a fabricated demo catalog; the actual branch's configured sale-unit prices
are shown, not an editable amount generated by the browser.

During a queue, four taps add the four items. The sticky, mobile-accessible
order total is ₵40; the seller taps Take payment then the large "Cash paid"
confirmation *after receiving physical cash*. The existing canonical
SALE_CREATE handler sends an idempotent mutation and verifies authoritative
server pricing/stock/accounting. The cart only auto-resets after the server
reports APPLIED with a COMPLETED cash sale. It never auto-resets on REJECTED,
RECEIVED or uncertain status. An unchanged retry reuses the same mutation ID.

Offline, a sale is queued in the existing business-scoped durable localStorage
queue. The next order opens only after the local mutation persistence succeeds,
and the UI explicitly labels it as **not yet server-confirmed**. Offline
stock and prices remain estimates until the sync server accepts the entry.
The vendor must keep the device and periodically verify outstanding sync
entries. Do not erase browser/site data while unsynced sales exist.

For a larger cash note, exact change, MoMo, card, customer credit, special
pricing, or a receipt, use "Customer gave different cash / MoMo / credit /
print receipt". This opens the protected full checkout path, including
provider verification and any existing credit/approval restrictions.
A spoken or cash payment never falsely completes an electronic charge.

Quick Serve has tappable 2–4-column responsive tiles, an accessible search,
branch-specific device-local favourite pins (up to 30), and a persistent mobile
amount/payment control with expandable order line editing. Menu pins are local
to the browser and are not yet synchronized across staff devices. No new
permissions, payment provider, data table or backend financial handler is
introduced. The full POS is unchanged unless a seller opts into Quick Serve.

Source tests cover the ₵40 sample, minor money units, prepared-item priority,
pinned ordering and isolation, stock tile blocking, verified charge semantics,
mobile fixed control and the unchanged canonical sync path. Protected CI
(typecheck, API/web tests, desktop and visual QA) and staging deployment are
separate. This is not a claim that the feature has already been deployed.

## Portion-price buttons (follow-up)
When the catalog has multiple sale units for a food item (e.g. Waakye Small
₵5, Standard ₵10 and Large ₵15), Quick Serve displays **one Waakye card**
with three large, independently tappable amount buttons. It is still a single
tap to add each actual catalog unit. The same feature works for Fish ₵10/₵20
and other configured sizes. Pinned unit prices appear first within the group,
and pinning a price brings its product group near the top. Grouping is strictly
by catalog item ID, never just a matching name, so tenant/product collisions
cannot silently mix pricing or stock. No arbitrary user-entered unapproved
unit price enters the canonical SALE_CREATE mutation.
