# TradeOS signed runtime release candidate
The existing pilot stays nondeployable and its installed auditor remains unchanged. The dedicated main-push GitHub workflow runtime-release.yml packages the same locked API, Next web/admin and migration inputs into a separate release archive with schemaVersion 2, deployable:true, environment:staging, requiresOperatorApproval:true and per-migration SHA-256 digests. The flag identifies the format only; it is not deployment authorization. The release-only extractor reuses bounded, no-follow extraction, requires the exact migration inventory and refuses pilot manifests. It creates only a temporary sandbox. The distinct verifier pins the exact signed source commit, main ref, archive bytes and release workflow signer.

Before any live migration or switch, the reviewed root-installed adapter must verify the exact current main and successful main-push release workflow, run the central capacity check, acquire the application release lock, authenticate and extract into quarantine, check backup freshness and restore evidence, compare migration checksums and reconcile pending financial work. Current baseline is 60 matching migrations with 61–64 pending; the synthetic upgrade/restore gate passed. The five unpublished historical events require genuine durable internal-feed delivery, never forced acknowledgement. Existing release/rollback metadata and PM2 launcher compatibility must be retained. No payment or external provider features may be enabled as a side effect. A source-light release must not be installed through the legacy build path. At 91% disk utilization the current backup/restore service holds by design; do not bypass this policy. Offsite recovery remains unverified. No operator activation mechanism is installed by this PR.

## Root-installed release intake
The separate root-signed-intake command is installable from an exact, clean, current-main checkout through install-root-signed-intake.sh. It pins every trusted verifier and entrypoint checksum, refuses overwrite, uses the existing app lock, authenticates the exact signed release workflow and archive, opens the quarantined runtime read-only to the app principal, and combines migration/finance observations with independently verified root-only backup checksums and restore evidence. Its report includes freshness, offsite verification state and explicit authorizedToDeploy:false. It returns nonzero for stale backup or unresolved readiness. It cannot modify database records, launch services or switch releases. This is the intake portion of the activation adapter; actual migration/activation must separately enforce quiescence, a fresh backup and rollback.
